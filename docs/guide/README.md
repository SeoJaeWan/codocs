# .codocs 작성 가이드

`.codocs`에는 YAML 파일마다 문서 하나를 작성한다. 각 파일의 최상위 값은 배열이나 문자열이 아닌 하나의 매핑이어야 한다.
문서는 이름을 붙여 찾아보고 참조할 수 있는 설명의 단위다. 개념의 정의뿐 아니라 규칙·조건·예외·판단 근거·작업 흐름을 담을 수 있다.

실행 가능한 가상 프로젝트는 [`examples/.codocs`](../../examples/.codocs)에 있다.

## 문서 형식

개념·규칙·작업 흐름을 같은 형식으로 작성한다. `type` 필드는 사용하지 않는다.

```yaml
id: sample-order
name: 가상 주문
definition: 가상 고객의 구매 요청이다.
domains:
  - sample-sales
examples:
  - 가상 주문 SAMPLE-001을 생성한다.
deprecatedAliases:
  - id: previous-order
    message: sample-order로 변경되었습니다.
```

필수 필드는 `id`, `name`, `definition`, `domains`다. `domains`에는 문자열이 하나 이상 있어야 한다.
`examples`는 문자열 배열, `deprecatedAliases`는 필수 `id`와 선택 `message`를 가진 객체 배열이다. 두 선택 배열은 비어 있어도 된다.
이전 ID는 현재 ID와 같은 형식을 사용하며 이전 코드 식별자의 매칭을 유지한다. 문서 간 참조와 ID 기반 조회·수정은 각각 현재 `name`과 현재 `id`를 사용한다.

여러 도메인에 걸친 흐름도 같은 형식을 사용한다.

```yaml
id: sample-fulfillment
name: 가상 주문 처리
definition: |
  구매 요청의 주문 항목과 처리 조건을 확인한다.
  확인한 뒤 배송 절차를 진행한다.
domains:
  - sample-sales
  - sample-delivery
kind: procedure
status: confirmed
```

`kind`는 `policy`, `procedure`, `decision`, `discussion` 중 하나이고 `status`는 `proposed`, `confirmed`, `deprecated` 중 하나다.
모든 문서에서 선택 속성을 함께 사용할 수 있으며 생략한 값은 자동으로 추가하지 않는다.

`kind`는 내용의 성격을 나타낸다. `policy`는 규칙, `procedure`는 절차, `decision`은 선택과 판단 근거, `discussion`은 논의할 쟁점과 대안이다.

`status`는 내용의 합의·적용 상태를 나타낸다.

| 값           | 의미                                     |
| ------------ | ---------------------------------------- |
| `proposed`   | 제안되어 검토 중인 내용                  |
| `confirmed`  | 합의된 내용                              |
| `deprecated` | 적용이 종료되어 참고용으로 보존하는 내용 |

개발 작업의 대기·진행·완료를 나타내지 않는다. `confirmed`도 구현 완료를 뜻하지 않는다. 생략하면 상태를 명시하지 않은 것이며 자동으로 확정하지 않는다.

## 공통 값 규칙

- ID는 소문자와 숫자를 하이픈으로 연결한다. 정규식은 `^[a-z0-9]+(?:-[a-z0-9]+)*$`다.
- 문서의 문자열 값은 비거나 공백뿐일 수 없다.
- 대소문자, 앞뒤 공백과 줄바꿈은 작성한 그대로 의미가 있다.
- 알려지지 않은 필드는 JSON 값이면 보존되지만 `unknown_field` 경고가 생긴다.
- `aliases`라는 사용자 필드는 이름 참조나 `deprecatedAliases`의 의미를 갖지 않는다.

사용자 필드에는 문자열, 유한한 숫자, boolean, null, 배열과 문자열 키 객체를 사용할 수 있다. `NaN`, 무한대, undefined, 함수, 순환 객체처럼 JSON으로 표현할 수 없는 값은 API 입력에서 거부된다.

## 기본 작성 지침

다음은 제품의 기본 권장 사항이다. 프로젝트의 목적과 독자에 맞게 조정할 수 있으며, 이 지침을 따르지 않았다는 이유로 검증 오류·경고를 만들거나 저장을 차단하지 않는다. 필수 필드·허용 값·참조 문법 등의 형식 검증은 별개다.

문서 이름이 가리키는 주제와 독자가 해결할 질문을 중심으로 작성한다.
용어의 의미·동작·정책·조건·예외·판단 근거와 책임을 설명한다.
상태 코드만 적지 않고 어떤 조건에서 발생하며 왜 그렇게 판단하는지, 어떤 예외가 있는지 설명한다.
확인되지 않은 이유는 확정 사실로 기록하지 않는다. 미합의 정책을 확정된 동작처럼 쓰거나 기록을 지워 확정된 것으로 만들지 않는다.

새 설명을 추가하기 전에 같은 주제를 다루는 원문을 찾아 먼저 보완한다.
다른 설명은 참조로 연결하고 대상 문서에서 무엇을 확인할 수 있으며 현재 설명에 왜 필요한지 드러낸다.
무엇을 연결하는지 설명하지 않는 “다른 문서를 따른다” 같은 문장만 남기지 않는다.
연결이 있다는 사실만으로 모든 관련 문서를 확인한 것으로 간주하지 않고 판단에 필요한 원문을 추가로 읽는다.

구현 예정·진행·완료 여부, 담당 작업과 PR·이슈 배정 등 개발 진행 상황은 작업 관리 도구에서 관리한다.
개발 진행 상황을 담는 별도 문서도 만들지 않는다. 구현이 계약과 다르면 수정할 작업을 이슈·PR에 기록한다.

### 문서의 목적과 책임

첫 설명에서 무엇을 다루고 독자가 어떤 질문을 해결할 수 있는지 밝힌다.
작업을 설명한다면 무엇을 받아 어떤 판단을 하고 무엇을 반환하거나 변경하는지 적는다.
예를 들어 ‘반품 요청’은 요청의 의미와 정보를, ‘반품 승인’은 요청과 구매 내역을 확인해 승인 여부를 결정하는 과정을 설명할 수 있다.

용어 자체의 의미·구조·성질은 용어를 설명하는 문서에 둔다.
그 용어를 언제 선택하고 어떻게 사용하는지는 해당 작업에서 용어를 참조하며 설명한다.
‘반품 요청’ 문서가 승인과 환불 등 모든 사용처의 처리 규칙까지 담을 필요는 없다.

다른 처리에서 받은 정보를 사용할 때는 어떤 정보를 왜 사용하는지 설명한다.
그 정보의 구조나 계산 방법을 사용처에서 다시 정의하지 않는다.
별도 담당 문서가 없고 현재 주제에 필요한 동작이면 같은 문서에서 설명할 수 있다.
독립적인 질문으로 분리할 때는 기존 설명도 옮기며, 이 구분을 위해 새 문서 타입이나 고정된 절 제목을 만들 필요는 없다.

### 설명의 원본과 연결

정의·규칙·판단 기준은 담당 문서 한 곳에서 관리한다.
다른 문서에서는 그 설명이 필요한 상황과 관계를 적고 참조한다. 표현을 바꾸거나 일부만 요약해도 같은 조건·예외를 다시 규정하면 중복 관리가 된다.

예를 들어 반품 가능 조건을 ‘반품 정책’에서 정했다면 주문 처리 문서에는 그 조건표를 복사하지 않는다.
주문 처리에서 반품 가능 여부를 판단할 때 해당 정책을 확인해야 한다는 맥락과 연결을 남긴다.
현재 상황에 적용하는 예시는 둘 수 있지만 예시의 조건을 새로운 일반 규칙으로 만들지 않는다.

설명을 분리할 때는 기존 위치의 설명을 참조로 대체한다.
중복을 제거한 뒤 독립적으로 답할 질문이 남지 않는 문서는 합치고 참조를 갱신한다.
규칙 하나를 바꾸기 위해 여러 문서의 같은 설명을 고쳐야 한다면 중복 관리 여부를 확인한다.

### 문단과 간격

같은 설명에 속하는 문장은 줄바꿈으로 이어서 작성한다.
설명의 관점·조건·단계가 바뀔 때 빈 줄로 문단을 나눈다.
제목·목록·표는 주변 문단과 구분하며 YAML 들여쓰기를 유지한다.
문장마다 빈 줄을 넣거나 모든 빈 줄을 일괄 제거하지 않는다.

## 설명 범위와 분리 권장

설명 분리는 한 문서의 일부를 독립적으로 찾고 유지할 문서로 나눌지 판단하는 작업이다.
한 주제를 설명하는 데 여러 개념이 필요하다는 이유만으로 문서를 나누지 않는다.
다른 설명이 필요하면 참조를 연결하고 현재 주제에서 필요한 이유·순서를 적는다. 대상 문서의 규칙 전체를 복제하지 않는다.

다음은 프로젝트의 독자와 유지 방식에 맞게 조정할 수 있는 권장 기준이다.

| 판단 기준                                | 권장 처리                                                |
| ---------------------------------------- | -------------------------------------------------------- |
| 다른 곳에서도 같은 설명이 필요하다       | 기존 문서를 먼저 확인하고 필요하면 별도 문서로 분리한다. |
| 이름을 붙여 따로 찾아볼 만한 주제다      | 별도 문서로 분리한다.                                    |
| 다른 내용과 독립적으로 변경되는 규칙이다 | 별도 문서로 분리한다.                                    |
| 현재 주제 안에서만 의미 있는 조건·예외다 | 현재 문서에 유지한다.                                    |
| 길지만 계속 같은 질문에 답하고 있다      | 우선 제목·문단으로 정리한다.                             |

분리한 문서는 다른 곳에서 찾아 읽어도 주제와 적용 조건을 이해할 수 있게 작성한다.
원래 문서에는 연결과 함께 설명이 필요한 시점·이유를 남긴다. 단순 참조 목록만 남겨 원래 질문에 대한 답을 잃지 않는다.
참조 횟수나 문장 길이만으로 자동 분리하지 않는다.

형식·ID 및 이름 충돌·참조 오류를 검증하며 문서의 서술 방식이나 자연어 규칙의 타당성을 자동 판정하지 않는다.

## 이름과 폴더 구성

`id`는 프로젝트 내 유일한 영어 식별자이며 코드 매칭 기준이다. `name`은 원하는 언어의 문서 이름이며 본문 참조와 표시의 기준이다. `name`은 코드 매칭에 사용하지 않는다.
ID만 변경하고 문서용 이름을 유지하면 본문 참조는 유지된다. 코드 매칭은 현재 `id`와 `deprecatedAliases[].id`를 사용하며, 이전 ID에는 선택적인 `message`로 변경 안내를 남긴다. `aliases` 같은 사용자 필드는 코드 매칭이나 이름 참조에 사용하지 않는다.

`deprecatedAliases`의 항목은 `id`를 반드시 가지며 현재 ID와 같은 형식 규칙을 적용한다. 이전 ID가 현재 ID와 같으면 `invalid_field_value` 경고가 발생하지만 작성한 항목은 자동 삭제하지 않는다. ID 중복 검사는 변경 이력을 추적하지 않는다.

도메인은 문서가 설명하는 책임·주제의 분류이며 `domains`에 명시한다. 한 문서가 여러 책임을 함께 설명하면 여러 도메인에 속할 수 있다.
다른 영역의 문서를 참조한다는 이유만으로 그 영역에도 소속시키지 않는다.
폴더는 주제·도메인별로 묶을 수 있으며 제품이 고정 계층을 요구하지 않는다. 소속을 파일 경로에서 추론하지 않는다.

도메인 소개는 그 영역의 책임과 관련 문서가 답하는 질문을 안내한다.
도메인 소개와 개별 문서는 같은 형식이며 종류별 폴더로 구분할 필요가 없다.
패키지별 구성도 선택할 수 있지만 패키지와 도메인이 반드시 일치하는 것은 아니다.

## 이름 참조

참조는 ID가 아닌 문서의 `name`을 사용한다. 다음은 ‘문서’와 ‘설명 분리’라는 문서를 작성한 프로젝트의 예시다.

```yaml
definition: |
  [[문서]]에서 필수 속성을 확인하고 작성할 내용을 정한다.
  독립적으로 관리할 설명인지는 [[문서 작성 가이드:설명 분리]]의 기준으로 판단한다.
```

- 이름만 쓰면 모든 도메인의 통합 이름 공간에서 정확히 찾는다.
- 도메인과 이름을 콜론으로 구분하면 지정한 도메인 안에서 정확히 찾는다.
- 현재 문서의 도메인을 자동으로 우선하지 않는다.
- trim이나 대소문자 보정을 하지 않으므로 앞뒤 공백과 대소문자를 작성한 그대로 비교한다.
- 다른 도메인에 같은 이름이 있으면 도메인이 없는 참조는 모호할 수 있다.
- 자기 문서를 가리키는 참조는 연결하지 않는다.

참조는 `definition`과 문자열인 `examples` 원소에서만 찾는다. 이름·ID·사용자 필드에서 참조처럼 보이는 문자열은 해석하지 않는다.

## 참조 안의 특수 문자

참조를 여는 두 대괄호 바로 앞에 연속된 백슬래시가 홀수 개이면 리터럴이다. 이름이나 도메인에 들어가는 콜론은 `\:`로 작성한다.
예를 들어 도메인 `판매:동부`는 `판매\:동부`, 이름 `주문:확인`은 `주문\:확인`으로 적고 둘 사이의 구분 콜론만 escape하지 않는다.

```yaml
definition: |
  \[[문서]]는 연결하지 않는 글자다.
```

작은따옴표와 블록 문자열은 백슬래시를 그대로 보존한다. 큰따옴표 YAML 안에서는 백슬래시 자체를 한 번 더 escape한다.

```yaml
definition: "\\[[문서]]"
```

빈 이름이나 도메인, 추가로 escape하지 않은 콜론, 남은 대괄호와 닫히지 않은 참조는 `invalid_reference` 오류다.

## 이름 충돌과 불완전한 탐색

ID가 여러 발견 경로에 있으면 `duplicate_id`다. 같은 도메인에 같은 이름이 있으면 `duplicate_name`이다. 다른 도메인의 동명은 허용한다.

일부 파일이나 폴더를 읽지 못한 상태에서는 `scanStatus: partial`과 함께 확인한 결과를 성공으로 제공한다. 이전 색인에서 보존한 문서는 `confirmation: unconfirmed`와 마지막 원문 `revision`을 유지하고, `unconfirmed_reference` 진단으로 최신성·존재를 보장하지 않음을 알린다. 보이지 않은 후보가 있을 수 있으므로 색인에 없는 ID를 `not_found`로 확정하지 않으며, 전체 탐색이 완료된 `scanStatus: complete`에서만 부재·단일 대상·충돌을 다시 계산한다. 프로젝트나 `.codocs` 자체를 탐색하지 못한 `failed`는 `success: false`와 원인을 반환한다.

## YAML 표기

주석, 작은따옴표·큰따옴표, literal/folded 블록 문자열, 중첩 배열·매핑과 flow 표기를 사용할 수 있다. 단일 문서 표시 `---`도 허용한다.

다음 기능은 지원하지 않는다.

- 앵커와 별칭
- 병합 키
- 사용자 태그
- 한 파일의 복수 YAML 문서
- 중복 매핑 키

이 기능들은 `unsupported_yaml_feature` 오류가 된다. 일반 YAML 문법 오류, 빈 파일과 최상위 배열·스칼라는 `invalid_yaml`이다.
오류 코드와 함께 메시지와 위치를 확인해 해당 구문이나 값을 고친다.

## 내용 갱신과 이름 변경

개발 진행만 바뀌면 문서를 수정하지 않는다. 설명하는 의미·동작·정책이 바뀌면 담당 원문에 합의한 조건·근거·예외를 반영한다.
원문을 갱신한 뒤 그 내용을 사용하는 문서의 설명과 참조도 확인한다. 내용의 합의·적용 상태는 `status`로 표현하며 개발 진행도와 구분한다.

이름 변경 계산은 대상 이름 필드와 연결된 참조의 변경 후보를 보여준다.
모호한 참조나 여러 도메인은 사용자의 후보·도메인 선택이 필요할 수 있고, 같은 도메인의 새 이름 충돌은 변경을 차단한다.
미리보기의 `ready` 상태는 파일 저장 허용을 의미하지 않는다. 저장 기능은 최신 원문, 각 대상의 쓰기 가능 여부와 YAML 따옴표·escape를 다시 확인해야 한다.

명시적인 ID 변경 기능은 직전 ID를 `deprecatedAliases`에 보존하고 새 현재 ID가 이전 목록에 있으면 제거한다.
같은 이전 ID를 중복 추가하지 않고 작성한 변경 안내를 유지한다. YAML을 직접 편집할 때는 필요한 이전 ID 목록도 직접 관리한다.
update 요청의 `set`/`unset`으로는 `deprecatedAliases`를 직접 바꿀 수 없다. 이전 ID 목록은 ID를 실제로 변경할 때 자동으로 관리되며, 목록 자체를 고치려면 YAML을 직접 편집할 수 있다.
이전 ID 목록의 유지가 사용자 코드의 자동 변경이나 이전 ID를 통한 문서 조회를 의미하지 않는다.

## 이전 형식에서 옮기기

- `type`을 제거한다.
- `title`은 `name`, `body`는 `definition`으로 값 그대로 옮긴다.
- `domain` 문자열은 `domains` 배열로 감싸며 기존 복수 소속은 유지한다.
- 이름·ID·본문과 필요한 선택 속성을 보존하고 형식·충돌·참조를 검증한다.

이전 형식을 자동으로 해석하거나 변환하지 않는다. 예전 필드는 사용자 속성으로 보존·경고되며 새 필수 필드를 대신하지 않는다.
공개 TypeScript 성공 타입은 `Document`이며 이전 `Term`·`Knowledge` 타입은 제공하지 않는다.
