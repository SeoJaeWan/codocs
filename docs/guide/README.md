# .codocs 작성 가이드

`.codocs`에는 YAML 파일마다 문서 하나를 작성한다. 각 파일의 최상위 값은 배열이나 문자열이 아닌 하나의 매핑이어야 한다.

이 가이드의 작성 규칙은 프로젝트의 [기본 작성 지침](../../.codocs/document-model/basic-writing-guidelines.yaml)과 연결된 문서에서도 관리한다. 규칙을 변경할 때는 `.codocs`의 담당 문서를 먼저 수정한 뒤 이 가이드에 반영한다. 사용자가 가이드만으로도 작성법을 이해할 수 있도록 설명과 예시는 양쪽에 유지한다.

실행 가능한 가상 프로젝트는 [`examples/.codocs`](../../examples/.codocs)에 있다.

## 문서 형식

개념·규칙·작업 흐름을 같은 형식으로 작성한다. `type` 필드는 사용하지 않는다.

```yaml
id: sample-order
name: 가상 주문
definition: 가상 고객의 구매 요청이며 처리 순서는 [[가상 주문 처리]]에서 확인한다.
domains:
  - sample-sales
examples:
  - 가상 주문 SAMPLE-001을 생성한다.
deprecatedAliases:
  - id: previous-order
    message: 새 이름을 사용한다.
```

필수 필드는 `id`, `name`, `definition`, `domains`다. `domains`에는 문자열이 하나 이상 있어야 한다.
`examples`는 문자열 배열, `deprecatedAliases`는 현재 ID와 같은 형식을 따르는 필수 `id`와 선택 `message`를 가진 객체 배열이다. 두 선택 배열은 비어 있어도 된다.

여러 도메인에 걸친 흐름도 같은 형식을 사용한다.

```yaml
id: sample-fulfillment
name: 가상 주문 처리
definition: |
  [[sample-sales:가상 주문]]을 확인한다.
  확인한 뒤 가상 처리 절차를 진행한다.
domains:
  - sample-sales
  - sample-delivery
kind: procedure
status: confirmed
```

`kind`는 `policy`, `procedure`, `decision`, `discussion` 중 하나이고 `status`는 `proposed`, `confirmed`, `deprecated` 중 하나다.
모든 문서에서 선택 속성을 함께 사용할 수 있으며 생략한 값은 자동으로 추가하지 않는다.

`kind`는 내용의 성격을 나타낸다. `policy`는 규칙, `procedure`는 절차, `decision`은 선택과 판단 근거, `discussion`은 논의할 쟁점과 대안이다.

`status`는 내용의 합의·적용 상태를 나타낸다.

| 값           | 의미                                     |
| ------------ | ---------------------------------------- |
| `proposed`   | 제안되어 검토 중인 내용                  |
| `confirmed`  | 합의된 내용                              |
| `deprecated` | 적용이 종료되어 참고용으로 보존하는 내용 |

개발 작업의 대기·진행·완료를 나타내지 않는다. `confirmed`도 구현 완료를 뜻하지 않는다. 생략하면 상태를 명시하지 않은 것이며 자동으로 확정하지 않는다.

## 공통 값 규칙

- ID는 소문자와 숫자를 하이픈으로 연결한다. 정규식은 `^[a-z0-9]+(?:-[a-z0-9]+)*$`다.
- 문서의 문자열 값은 비거나 공백뿐일 수 없다.
- 대소문자, 앞뒤 공백과 줄바꿈은 작성한 그대로 의미가 있다.
- 알려지지 않은 필드는 JSON 값이면 보존되지만 `unknown_field` 경고가 생긴다.
- `aliases`라는 사용자 필드는 이름 참조나 `deprecatedAliases`의 의미를 갖지 않는다.

사용자 필드에는 문자열, 유한한 숫자, boolean, null, 배열과 문자열 키 객체를 사용할 수 있다. `NaN`, 무한대, undefined, 함수, 순환 객체처럼 JSON으로 표현할 수 없는 값은 API 입력에서 거부된다.

## 기본 작성 지침

다음은 제품의 기본 권장 사항이다. 프로젝트의 목적과 독자에 맞게 조정할 수 있으며, 이 지침을 따르지 않았다는 이유로 검증 오류·경고를 만들거나 저장을 차단하지 않는다. 필수 필드·허용 값·참조 문법 등의 형식 검증은 별개다.

- 문서 이름이 가리키는 주제와 독자가 해결할 질문을 중심으로 작성한다.
- 용어의 의미, 동작, 정책, 조건, 예외, 판단 근거와 책임을 설명한다.
- 같은 주제를 다루는 원문이 있으면 먼저 보완한다. 다른 설명은 참조로 연결하고 필요한 이유와 상황을 남긴다.
- 구현 예정·진행·완료 여부, 담당 작업과 PR·이슈 배정 등 개발 진행 상황은 문서에 넣지 않고 작업 관리 도구에서 관리한다.
- 개발 진행 상황을 담는 별도 문서도 만들지 않는다. 구현이 계약과 다르면 수정할 작업을 이슈·PR에 기록한다.
- 미합의 정책을 확정된 동작처럼 쓰거나 기록을 지워 확정된 것으로 만들지 않는다.
- 개발 진행만 바뀌면 문서를 수정하지 않는다. 설명하는 의미·동작·정책이 바뀌면 수정한다.
- 내용의 합의·적용 상태는 `status`로 표현하며 개발 진행도와 구분한다.

## 설명 범위와 분리 권장

문서 이름이 가리키는 주제와 독자가 해결할 질문을 중심으로 작성한다. 정의뿐 아니라 규칙·조건·예외·흐름을 담을 수 있다.
다른 설명이 필요하면 참조를 연결하고 현재 주제에서 필요한 이유·순서를 적는다. 대상 문서의 규칙 전체를 복제하지 않는다.

다음은 제품의 기본 권장 사항이다. 프로젝트에 맞춰 조정할 수 있으며 따르지 않아도 검증 오류·경고가 생기거나 저장이 차단되지 않는다.

| 판단 기준                                | 권장 처리                      |
| ---------------------------------------- | ------------------------------ |
| 다른 곳에서도 같은 설명이 필요하다       | 별도 문서로 분리하고 참조한다. |
| 이름을 붙여 따로 찾아볼 만한 주제다      | 별도 문서로 분리한다.          |
| 다른 내용과 독립적으로 변경되는 규칙이다 | 별도 문서로 분리한다.          |
| 현재 주제 안에서만 의미 있는 조건·예외다 | 현재 문서에 유지한다.          |
| 길지만 계속 같은 질문에 답하고 있다      | 우선 제목·문단으로 정리한다.   |

형식·ID 및 이름 충돌·참조 오류를 검증하며 문서의 서술 방식이나 자연어 규칙의 타당성을 자동 판정하지 않는다.

## 이름과 폴더 구성

`id`는 프로젝트 내 유일한 영어 식별자다. 코드 용어에 맞춰 변경할 수 있으며 향후 코드 매칭 기준으로 사용한다.
`name`은 원하는 언어의 문서 링크 식별자이며 본문 참조와 문서 표시의 기준이다. `name`은 코드 매칭 기준으로 사용하지 않는다.

ID만 변경하고 문서용 이름을 유지하면 본문 참조는 유지된다. 코드 매칭은 현재 `id`와 `deprecatedAliases[].id`를 사용하며, 이전 ID에는 선택적인 `message`로 변경 안내를 남긴다. `aliases` 같은 사용자 필드는 코드 매칭이나 이름 참조에 사용하지 않는다.

`deprecatedAliases`는 코드 매칭을 유지할 이전 ID의 객체 배열이다. 항목은 `id`를 반드시 가지며 현재 ID와 같은 형식 규칙을 적용한다. 이전 ID가 현재 ID와 같으면 `invalid_field_value` 경고가 발생하지만 작성한 항목은 자동 삭제하지 않는다. 예전 형식처럼 항목에 `name`만 작성하면 `unknown_field` 경고와 `missing_required_field` 오류가 함께 발생하며, 그 항목은 이전 ID로 매칭하지 않는다.

폴더는 주제·도메인별로 묶을 수 있으며 제품이 고정 계층을 요구하지 않는다. 소속은 `domains`에 명시하고 파일 경로에서 추론하지 않는다.
도메인 소개와 개별 문서는 같은 형식이며 종류별 폴더로 구분할 필요가 없다.

## 이전 형식에서 옮기기

- `type`을 제거한다.
- `title`은 `name`, `body`는 `definition`으로 값 그대로 옮긴다.
- `domain` 문자열은 `domains` 배열로 감싸며 기존 복수 소속은 유지한다.
- 이름·ID·본문과 필요한 선택 속성을 보존하고 형식·충돌·참조를 검증한다.

이전 형식을 자동으로 해석하거나 변환하지 않는다. 예전 필드는 사용자 속성으로 보존·경고되며 새 필수 필드를 대신하지 않는다.
공개 TypeScript 성공 타입은 `Document`이며 이전 `Term`·`Knowledge` 타입은 제공하지 않는다.

## 이름 참조

ID가 아닌 문서의 `name`을 참조한다.

```yaml
definition: |
  [[가상 주문]]
  [[sample-sales:가상 주문]]
```

- `[[이름]]`은 모든 도메인의 통합 이름 공간에서 정확히 찾는다.
- `[[도메인:이름]]`은 지정한 도메인 안에서 정확히 찾는다.
- 현재 문서의 도메인을 자동으로 우선하지 않는다.
- trim이나 대소문자 보정을 하지 않으므로 `[[ 주문]]`과 `[[주문]]`은 다른 이름이다.
- 다른 도메인에 같은 이름이 있으면 도메인이 없는 참조는 모호할 수 있다.
- 자기 문서를 가리키는 참조는 연결하지 않는다.

참조는 `definition`과 문자열인 `examples` 원소에서만 찾는다. 이름·ID·사용자 필드에서 참조처럼 보이는 문자열은 해석하지 않는다.

## 참조 안의 특수 문자

참조 시작 `[[` 바로 앞에 연속된 백슬래시가 홀수 개이면 리터럴이다. 이름이나 도메인에 들어가는 콜론은 `\:`로 작성한다.

```yaml
definition: |
  \[[가상 주문]]는 연결하지 않는 글자다.
  [[판매\:동부:주문\:확인]]
```

두 번째 참조의 도메인은 `판매:동부`, 이름은 `주문:확인`이다.

작은따옴표와 블록 문자열은 백슬래시를 그대로 보존한다. 큰따옴표 YAML 안에서는 백슬래시 자체를 한 번 더 escape한다.

```yaml
definition: "\\[[가상 주문]]"
```

빈 이름이나 도메인, 추가로 escape하지 않은 콜론, 남은 대괄호와 닫히지 않은 참조는 `invalid_reference` 오류다.

## 이름 충돌과 불완전한 탐색

ID가 여러 발견 경로에 있으면 `duplicate_id`다. 같은 도메인에 같은 이름이 있으면 `duplicate_name`이다. 다른 도메인의 동명은 허용한다.

일부 파일이나 폴더를 읽지 못한 상태에서는 `scanStatus: partial`과 함께 확인한 결과를 성공으로 제공한다. 이전 색인에서 보존한 문서는 `confirmation: unconfirmed`와 마지막 원문 `revision`을 유지하고, `unconfirmed_reference` 진단으로 최신성·존재를 보장하지 않음을 알린다. 보이지 않은 후보가 있을 수 있으므로 색인에 없는 ID를 `not_found`로 확정하지 않으며, 전체 탐색이 완료된 `scanStatus: complete`에서만 부재·단일 대상·충돌을 다시 계산한다. 프로젝트나 `.codocs` 자체를 탐색하지 못한 `failed`는 `success: false`와 원인을 반환한다.

## YAML 표기

주석, 작은따옴표·큰따옴표, literal/folded 블록 문자열, 중첩 배열·매핑과 flow 표기를 사용할 수 있다. 단일 문서 표시 `---`도 허용한다.

다음 기능은 지원하지 않는다.

- 앵커와 별칭
- 병합 키
- 사용자 태그
- 한 파일의 복수 YAML 문서
- 중복 매핑 키

이 기능들은 `unsupported_yaml_feature` 오류가 된다. 일반 YAML 문법 오류, 빈 파일과 최상위 배열·스칼라는 `invalid_yaml`이다.

## 이름 변경 미리보기

이름 변경 계산은 대상 이름 필드와 연결된 참조의 변경 후보를 보여준다. 모호한 참조나 여러 도메인은 사용자의 후보·도메인 선택이 필요할 수 있고, 같은 도메인의 새 이름 충돌은 변경을 차단한다.

미리보기의 `ready` 상태는 파일 저장 허용을 의미하지 않는다. 저장 기능은 최신 원문, 각 대상의 쓰기 가능 여부와 YAML 따옴표·escape를 다시 확인해야 한다.
